# LangChain 후기 분석 Tauri 앱 PRD

## 1. 문서 상태

- 상태: 승인됨, MVP 구현 및 macOS arm64 패키징 검증 완료
- 대상 릴리스: MVP
- 문서 범위: 제품 요구사항과 구현 단계 정의
- 코드 구현과 README 개편은 별도 구현 계획에서 추적하며 이 문서를 제품 요구사항의 기준으로 사용한다.

### 1.1 2026-07-22 구현 검증 결과

- Tauri 런처, 후기 직접 입력과 CSV 입력, 제한 동시성 분석, 부분 실패, 재시도, 취소, 답변 편집과 복사, CSV와 JSON 내보내기를 구현했다.
- Python sidecar, Rust 명령 계층, React 웹뷰의 계약 버전과 입력 범위를 각각 검증한다.
- 로컬 Ollama `gemma4:e2b`에서 후기 1건의 구조화 분석과 답변 후보 3개 생성을 확인했다.
- macOS arm64 앱과 DMG를 생성하고 앱 번들의 ad-hoc 서명과 DMG 체크섬을 검증했다.
- 375px, 768px, 1280px에서 가로 넘침이 없고 키보드로 프로그램에 진입할 수 있음을 확인했다.
- Windows와 Linux 패키징, Groq와 OpenAI의 실제 자격 증명 호출, Apple Developer ID 서명과 공증은 후속 검증 범위다.

## 2. 요청 전처리와 실행 메타 프롬프트

### 2.1 사용자 요청 해석

- 하나의 Tauri 데스크톱 앱에서 여러 프로그램을 선택할 수 있어야 한다.
- 첫 번째 프로그램은 여러 상품 후기를 입력받아 LangChain으로 병렬 분석한다.
- 각 후기에서 긍정, 부정 또는 중립 감성, 요약, 핵심 내용, 답변 전략을 생성한다.
- 사용자가 바로 활용할 수 있는 답변 후보를 여러 개 생성한다.
- 결과는 화면 표시, 재처리, 내보내기가 가능한 구조화 데이터로 반환한다.
- 저장소의 메인 `README.md`는 후기 분석 앱과 멀티 프로젝트 런처를 중심으로 후속 개편한다.

### 2.2 실행 메타 프롬프트

> 최신 안정 버전의 Tauri v2, React, TypeScript, Rust, Python, LangChain, Pydantic을 기준으로 크로스플랫폼 데스크톱 앱의 제품 요구사항을 정의한다. 앱은 프로그램 선택 런처와 독립된 프로그램 모듈을 제공하며, 첫 모듈은 여러 상품 후기를 입력받아 제한된 동시성으로 병렬 분석한다. 각 결과는 감성, 한 줄 요약, 핵심 포인트, 답변 전략, 서로 다른 말투의 답변 후보 3개, 처리 상태와 오류를 Pydantic 스키마로 검증하여 반환한다. 원본 순서를 보존하고 일부 실패가 전체 작업을 중단하지 않게 한다. API 키와 원문 후기는 웹뷰와 로그에 노출하지 않는다. 현재 저장소의 Python 3.12와 Ollama 중심 구성을 재사용하되 Groq와 OpenAI를 선택 가능한 모델 제공자로 둔다. 향후 새 프로그램을 런처 등록 정보만 추가하여 확장할 수 있는 구조와 README 개편 요구까지 포함한다.

## 3. 제품 개요

### 3.1 제품 한 줄 정의

여러 상품 후기를 한 번에 분석하고 실무 답변 후보까지 만드는 로컬 우선 AI 데스크톱 도구 모음이다.

### 3.2 해결하려는 문제

판매자와 고객 응대 실무자는 후기마다 감정을 파악하고 핵심 문제를 요약한 뒤 적절한 답변을 직접 작성해야 한다. 후기가 많을수록 작업 시간이 늘고 답변 품질과 말투가 달라진다. 기존 범용 AI 채팅은 각 후기의 입력과 결과를 별도로 관리해야 하며, 실패한 요청만 다시 처리하거나 결과를 표 형태로 내보내기 어렵다.

### 3.3 제품 가치

- 반복 작업 감소: 여러 후기를 한 번에 입력하고 제한된 동시성으로 처리한다.
- 일관된 결과: 모든 분석을 동일한 구조와 검증 규칙으로 반환한다.
- 답변 작성 지원: 단순 감성 분류에서 끝내지 않고 바로 수정하여 쓸 수 있는 답변 후보를 제공한다.
- 로컬 우선 선택권: Ollama를 기본값으로 사용하고 필요할 때 클라우드 모델을 선택한다.
- 확장 가능한 도구 모음: 후기 분석 외 프로그램을 같은 Tauri 런처에 추가한다.

## 4. 목표와 비목표

### 4.1 MVP 목표

1. 사용자가 Tauri 메인 화면에서 후기 분석 프로그램을 선택해 진입한다.
2. 사용자가 여러 후기를 직접 붙여넣거나 CSV 파일로 입력한다.
3. 각 후기를 독립적으로 병렬 분석하고 진행률을 실시간으로 표시한다.
4. 각 결과를 감성, 요약, 핵심 포인트, 답변 전략, 답변 후보 3개로 구조화한다.
5. 일부 분석이 실패해도 성공한 결과를 유지하고 실패한 항목만 다시 처리한다.
6. 결과를 원본 입력 순서로 확인하고 CSV 또는 JSON으로 내보낸다.
7. 새 프로그램이 추가될 때 런처의 공통 틀을 다시 설계하지 않도록 확장 계약을 정의한다.

### 4.2 비목표

- 쇼핑몰, 배달 앱, SNS에서 후기를 자동 수집하지 않는다.
- 사용자 승인 없이 외부 서비스에 답변을 자동 게시하지 않는다.
- 여러 사용자가 동시에 접속하는 서버형 서비스로 운영하지 않는다.
- 자체 모델 학습이나 파인튜닝을 수행하지 않는다.
- 최초 MVP에서 동적 플러그인 설치와 제3자 플러그인 실행을 지원하지 않는다.
- 후기 원문을 원격 데이터베이스에 동기화하지 않는다.

## 5. 대상 사용자

### 5.1 핵심 사용자

- 온라인 판매자: 상품 후기를 빠르게 분류하고 답변해야 한다.
- 고객 응대 실무자: 브랜드 말투를 유지하면서 불만과 칭찬에 대응해야 한다.
- 소규모 브랜드 운영자: 별도 분석 시스템 없이 반복되는 후기 내용을 파악해야 한다.

### 5.2 주요 사용자 요구

- AI 도구에 익숙하지 않아도 입력부터 결과 저장까지 한 화면 흐름으로 처리할 수 있어야 한다.
- 어떤 항목이 처리 중이고 어떤 항목이 실패했는지 바로 알아야 한다.
- AI가 만든 답변을 그대로 게시하기 전에 비교하고 수정할 수 있어야 한다.
- API 키, 후기 원문, 분석 이력이 어디에서 처리되는지 알 수 있어야 한다.

## 6. 제품 원칙

1. 원문 보존: AI 결과가 원문을 덮어쓰지 않는다.
2. 사람이 최종 결정: 답변은 추천안이며 자동 게시하지 않는다.
3. 부분 실패 허용: 한 후기의 실패가 전체 작업을 무효화하지 않는다.
4. 구조 우선: 자유 형식 텍스트보다 검증 가능한 구조화 출력을 우선한다.
5. 로컬 우선: 기본 모델은 Ollama이며 외부 전송은 사용자가 클라우드 모델을 선택한 경우에만 발생한다.
6. 최소 권한: 웹뷰, Rust, Python sidecar 사이의 접근 권한을 필요한 범위로 제한한다.
7. 확장 계약 우선: 프로그램별 기능은 런처 공통 코드와 분리한다.

### 7.2 가정

- 초기 사용자는 macOS에서 먼저 검증하되 Windows와 Linux를 막는 플랫폼 전용 설계는 피한다.
- 후기 한 건은 일반적인 쇼핑몰 후기 길이를 기준으로 하며 지나치게 긴 입력은 사용자에게 축약 또는 분할을 요청한다.
- 클라우드 모델을 선택하면 후기 원문이 해당 모델 제공자에게 전송된다는 안내와 확인이 필요하다.
- 모델별 결과 품질과 처리 속도는 다르므로 동일한 고정 시간보다 진행 상태와 실패 복구를 우선한다.

## 8. 핵심 사용자 흐름

### 8.1 프로그램 선택

1. 사용자가 앱을 실행한다.
2. 메인 런처에서 사용 가능한 프로그램 카드를 확인한다.
3. `상품 후기 분석`을 선택한다.
4. 후기 분석 프로그램의 입력 화면으로 이동한다.
5. 사용자는 언제든 런처로 돌아갈 수 있다.

### 8.2 후기 분석

1. 사용자가 상품명과 선택 정보인 브랜드 말투를 입력한다.
2. 여러 후기 문장을 붙여넣거나 CSV 파일을 선택한다.
3. 앱이 빈 후기, 중복 후기, 길이 초과, CSV 열 오류를 사전 검사한다.
4. 사용자가 모델 제공자와 모델을 선택한다.
5. 클라우드 모델인 경우 외부 전송 안내를 확인한다.
6. 사용자가 분석을 시작한다.
7. 완료 수, 실패 수, 전체 수와 개별 상태가 갱신된다.
8. 완료된 결과는 끝나는 순서대로 표시되지만 원본 순서로 정렬할 수 있다.
9. 사용자가 답변 후보를 비교하고 필요한 문구를 수정하거나 복사한다.
10. 사용자가 전체 결과를 CSV 또는 JSON으로 내보낸다.

### 8.3 실패 복구

1. 실패한 후기는 오류 상태와 재시도 가능 여부를 표시한다.
2. 사용자는 실패한 항목만 선택하여 다시 처리한다.
3. 재시도 성공 시 기존 실패 상태를 새 결과로 교체한다.
4. 취소된 작업은 완료된 결과를 유지하고 아직 시작하지 않은 항목을 취소 상태로 둔다.

| MODEL-004 | 클라우드 모델 선택 시 외부 전송 안내를 표시한다. | 필수 | 확인 전에는 분석 요청을 보내지 않는다. |
| MODEL-005 | 제공자별 모델 호출을 공통 LangChain 인터페이스 뒤에 둔다. | 필수 | 분석 파이프라인을 변경하지 않고 제공자를 바꿀 수 있다. |

### 9.4 분석과 병렬 처리

| ID | 요구사항 | 우선순위 | 승인 기준 |
|---|---|---|---|
| ANALYSIS-001 | 각 후기를 독립 LangChain 입력으로 분석한다. | 필수 | 다른 후기 내용이 현재 결과에 섞이지 않는다. |
| ANALYSIS-002 | Pydantic 모델로 구조화 결과를 검증한다. | 필수 | 필수 필드가 없거나 enum 값이 잘못되면 성공으로 처리하지 않는다. |
| ANALYSIS-003 | `batch_as_completed()` 또는 동등한 완료 이벤트 흐름을 사용한다. | 필수 | 먼저 끝난 결과가 전체 배치 완료 전 화면에 반영된다. |
| ANALYSIS-004 | `max_concurrency`로 동시 호출 수를 제한한다. | 필수 | 기본값 4와 설정값 1부터 8까지가 실제 실행 제한에 반영된다. |
| ANALYSIS-005 | 한 항목의 실패를 해당 항목에만 기록한다. | 필수 | 일부 실패 후에도 다른 항목의 결과가 유지된다. |
| ANALYSIS-006 | 사용자가 진행 중 작업을 취소할 수 있다. | 권장 | 새 요청 시작을 중단하고 완료된 결과는 유지한다. |
| ANALYSIS-007 | 실패 항목만 선택하여 재시도할 수 있다. | 필수 | 성공 항목을 다시 호출하지 않고 실패 항목 상태만 갱신한다. |
| ANALYSIS-008 | 결과를 원본 순번으로 재정렬할 수 있다. | 필수 | 완료 순서와 원본 순서 보기를 모두 제공한다. |
| ANALYSIS-009 | 후기 원문을 신뢰할 수 없는 데이터로 취급한다. | 필수 | 후기 안의 명령문이 시스템 지침이나 출력 스키마를 변경하지 못하고 외부 도구를 실행하지 않는다. |
| ANALYSIS-010 | Python, Rust, TypeScript 사이의 메시지 계약 버전을 검증한다. | 필수 | 지원하지 않는 계약 버전은 명시적 오류로 중단하고 잘못된 필드는 성공 상태로 전달하지 않는다. |

| RESULT-003 | 칭찬, 불만, 요청 등 핵심 포인트를 목록으로 반환한다. | 필수 | 0개부터 5개까지의 짧은 항목으로 표시한다. |

## 11. 전체 작업 요약

작업 완료 시 다음 집계를 제공한다.

- 전체 후기 수, 성공 수, 실패 수, 취소 수
- 긍정, 부정, 중립 개수와 비율
- 반복되는 칭찬과 불만 주제
- 우선 확인이 필요한 부정 후기 목록
- 재시도 가능한 실패 수
- 사용한 모델 제공자, 모델, 시작 시각, 종료 시각

전체 작업 요약은 개별 결과를 집계하여 생성한다. LLM이 계산한 수치를 그대로 신뢰하지 않고 애플리케이션 코드가 개수와 비율을 계산한다.

## 12. 시스템 아키텍처

### 12.1 권장 구조

```text
Tauri 메인 런처와 React 웹뷰
  -> 허용된 Tauri invoke 명령
Rust 애플리케이션 계층
  -> 입력 검증, 작업 생명주기, sidecar 권한과 프로세스 관리
Python sidecar
  -> LangChain Runnable, Pydantic 구조 검증, 제공자 어댑터
Ollama 또는 사용자가 선택한 클라우드 모델
```

### 12.2 구성 요소 책임

| 구성 요소 | 책임 | 하지 않는 일 |
|---|---|---|
| React 웹뷰 | 입력, 진행률, 결과 비교, 수정, 내보내기 요청 | API 키 직접 저장, 모델 직접 호출 |
| Rust 계층 | 권한, 명령 검증, 작업 상태, sidecar 실행과 종료, 이벤트 전달 | 후기 의미 분석 |
| Python sidecar | 프롬프트 구성, 제한된 병렬 호출, 구조 검증, 오류 표준화 | UI 렌더링, 임의 파일 접근 |
| 모델 제공자 | 후기 분석 결과 생성 | 작업 상태와 로컬 파일 관리 |

### 12.3 sidecar 통신 계약

- 웹뷰는 Python 프로세스를 직접 실행하지 않고 허용된 Rust 명령만 호출한다.
- Rust는 Tauri `externalBin`에 등록된 sidecar만 실행한다.
- Tauri Capabilities에는 필요한 명령과 sidecar 실행 권한만 허용한다.
- Rust와 Python은 버전이 명시된 JSON 메시지로 통신한다.
- Pydantic 모델에서 내보낸 JSON Schema와 공통 계약 픽스처를 기준으로 Rust serde 구조체와 TypeScript 타입의 호환성을 검사한다.
- 각 요청과 이벤트는 `job_id`, `review_id`, `source_index`를 포함한다.
- stdout은 구조화 이벤트 전용으로 사용하고 진단 로그는 원문과 비밀값을 제거한 별도 채널로 보낸다.
- 앱 종료 시 sidecar와 진행 중 작업을 정리한다.

### 12.4 프로그램 확장 계약

각 프로그램은 다음 등록 정보를 제공한다.

| 필드 | 설명 |
|---|---|
| `id` | 중복되지 않는 프로그램 식별자 |
| `title` | 런처에 표시할 이름 |
| `description` | 한 문장 설명 |
| `icon` | 앱에 포함된 아이콘 참조 |
| `route` | 프로그램 진입 경로 |
| `status` | `available`, `beta`, `coming_soon`, `disabled` |
| `version` | 프로그램 기능 버전 |
| `required_capabilities` | 필요한 Tauri 권한 목록 |

MVP에서는 앱 빌드 시 포함되는 내부 등록 방식을 사용한다. 외부에서 임의 코드를 설치하는 동적 플러그인 시스템은 보안과 업데이트 정책이 확정될 때까지 지원하지 않는다.

## 13. 아키텍처 대안 비교

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Python sidecar와 Rust IPC | 현재 Python LangChain 자산 재사용, 로컬 포트 불필요, 권한 경계 명확 | 실행 파일 패키징과 프로세스 생명주기 검증 필요 | MVP 권장 |
| Python FastAPI 로컬 서버 | HTTP, SSE, API 테스트가 쉬움 | 포트 충돌, 로컬 인증, 서버 종료, 방화벽 고려 필요 | 복수 클라이언트 요구가 생길 때 재검토 |
| LangChain.js 직접 실행 | Node 계층 통일, Python 패키징 불필요 | 현재 Python 자산 재사용 어려움, 웹뷰 비밀값 노출 위험, Rust 경계 우회 가능 | MVP 제외 |

## 14. 병렬 처리 정책

### 14.1 실행 방식

1. 입력 검증을 통과한 후기마다 독립 작업을 만든다.
2. LangChain의 배치 또는 비동기 배치 실행에 `max_concurrency`를 적용한다.
3. 완료 이벤트를 받는 즉시 해당 후기의 상태와 결과를 갱신한다.
4. 화면은 완료 순서와 원본 순서를 모두 지원한다.
5. 집계 수치는 성공 결과가 도착할 때마다 애플리케이션 코드가 다시 계산한다.

### 14.2 동시성 제한

- 기본값은 4이다.
- 사용자는 1부터 8 사이에서 선택할 수 있다.
- 제공자 제한 또는 로컬 자원 부족이 확인되면 새 작업 시작을 잠시 멈추고 현재 상태를 표시한다.
- 재시도는 실패 원인을 확인한 뒤 실패 항목에만 적용한다.
- 무제한 자동 재시도는 하지 않는다.

### 14.3 순서와 일관성

- `source_index`를 결과 정렬의 기준으로 사용한다.
- 동일 `review_id`의 늦게 도착한 이전 요청 결과가 최신 재시도 결과를 덮어쓰지 않도록 실행 시도 번호를 둔다.
- 취소 요청 이후 새 모델 호출을 시작하지 않는다.
- 이미 완료된 결과는 취소 때문에 삭제하지 않는다.

## 15. 오류 처리

| 상황 | 사용자 표시 | 시스템 동작 |
|---|---|---|
| Ollama 미실행 | 로컬 모델에 연결할 수 없음 | 실행 중단, 연결 확인 방법 제공 |
| 잘못된 API 키 | 인증 정보를 확인해야 함 | 해당 제공자 요청 중단, 키 값은 표시하지 않음 |
| 호출 제한 | 잠시 후 재시도 필요 | 해당 항목 실패 처리, 재시도 가능 표시 |
| 응답 시간 초과 | 모델 응답 시간이 초과됨 | 해당 항목만 종료하고 다른 작업 계속 |
| 스키마 검증 실패 | 결과 형식을 확인하지 못함 | 성공 결과로 저장하지 않고 재시도 가능 표시 |
| CSV 형식 오류 | 후기 열을 읽을 수 없음 | 분석 시작 전 행과 열 문제 표시 |
| sidecar 종료 | 분석 서비스가 중단됨 | 진행 중 항목 실패 처리, 재시작 안내 |
| 내보내기 실패 | 파일을 저장하지 못함 | 기존 화면 결과 유지, 경로 또는 권한 문제 표시 |

예외를 숨기거나 빈 성공 결과로 바꾸지 않는다. 사용자 메시지와 진단 정보를 분리하고 진단 정보에서도 API 키와 후기 원문을 제거한다.

## 16. 보안과 개인정보

### 16.1 비밀값

- API 키를 소스, README, 로그, 웹뷰 상태, `localStorage`에 저장하지 않는다.
- 가능한 경우 운영체제 자격 증명 저장소를 사용한다.
- Python sidecar에는 선택한 요청에 필요한 자격 증명만 프로세스 환경 또는 제한된 IPC로 전달한다.
- 오류 메시지와 내보내기 파일에 API 키를 포함하지 않는다.

### 16.2 후기 원문

- Ollama 사용 시 후기 원문은 로컬 처리 범위를 벗어나지 않는다.
- 클라우드 모델 선택 시 제공자 전송 사실을 분석 시작 전에 알린다.
- 원문 전체를 일반 로그와 충돌 보고서에 기록하지 않는다.
- MVP는 자동 클라우드 동기화와 원격 분석 이력 저장을 하지 않는다.
- 사용자가 내보내기를 선택한 경우에만 지정한 경로에 결과 파일을 생성한다.

### 16.3 Tauri 권한

- 각 창과 웹뷰에 필요한 Capability만 연결한다.
- 임의 셸 실행, 임의 파일 읽기와 쓰기를 허용하지 않는다.
- 파일 열기와 저장은 사용자가 선택한 경로에만 허용한다.
- sidecar 이름과 허용 인자를 고정하고 웹뷰 입력을 그대로 명령행으로 연결하지 않는다.

### 16.4 신뢰할 수 없는 후기와 파일

- 후기 원문은 프롬프트 안의 명령이 아니라 분석할 데이터로 명확히 구분한다.
- 후기 분석 체인에는 웹 검색, 파일 접근, 셸 실행과 같은 도구를 연결하지 않는다.
- 모델 출력은 실행 가능한 명령으로 취급하지 않고 Pydantic 스키마를 통과한 데이터만 표시한다.
- CSV 내보내기에서는 `=`, `+`, `-`, `@`로 시작하는 셀이 스프레드시트 수식으로 실행되지 않도록 안전하게 처리한다.
- 가져온 파일 경로와 내용은 사용자가 시작한 분석과 내보내기 이외의 목적으로 사용하지 않는다.

## 17. 비기능 요구사항

### 17.1 성능

- 앱은 분석 중에도 입력과 결과 목록 스크롤에 응답해야 한다.
- 첫 완료 결과가 도착하면 전체 작업 종료를 기다리지 않고 표시한다.
- 200건 입력에서도 화면에 필요한 행만 렌더링하도록 목록 가상화를 검토한다.
- 성능 목표는 모델과 장비별 기준 측정 후 처리량과 첫 결과 시간으로 기록한다.

### 17.2 신뢰성

- 일부 실패가 성공 결과를 삭제하지 않는다.
- 재시도는 성공 항목을 중복 호출하지 않는다.
- 앱 또는 sidecar가 비정상 종료되어도 비밀값을 파일에 남기지 않는다.
- 내보내기 전까지 현재 세션 결과를 메모리에 유지한다.

### 17.3 접근성과 사용성

- 마우스 없이 프로그램 선택, 입력, 분석 시작, 결과 이동, 복사가 가능해야 한다.
- 감성은 색상만으로 구분하지 않고 텍스트 라벨을 함께 표시한다.
- 진행률과 오류 상태를 보조 기술이 읽을 수 있는 텍스트로 제공한다.
- 파괴적 동작과 분석 취소에는 명확한 확인 절차를 둔다.

### 17.4 호환성

- macOS를 첫 검증 대상으로 한다.
- 경로, 파일 인코딩, 프로세스 실행은 Windows와 Linux 확장을 막지 않게 설계한다.
- CSV 내보내기는 UTF-8과 한글 데이터를 보존한다.

## 19. 성공 지표

### 19.1 제품 지표

- 사용자가 앱 실행부터 첫 분석 시작까지 별도 개발 도구 없이 완료할 수 있다.
- 20건 후기 기준으로 개별 복사와 분석을 반복하는 방식보다 사용자 조작 단계가 줄어든다.
- 사용자가 답변 후보 중 하나를 선택하거나 수정하여 복사할 수 있다.
- 실패 항목만 다시 처리하여 성공 결과의 중복 호출을 피할 수 있다.

### 19.2 품질 지표

- 정상 모델 응답의 구조화 스키마 검증 성공률 목표는 95% 이상이다.
- 부분 실패 시 성공 결과 보존율은 100%여야 한다.
- 원본 입력 순서 복원 정확도는 100%여야 한다.
- 내보낸 결과의 후기 수와 화면의 전체 상태 수가 일치해야 한다.
- 비밀값이 웹뷰, 일반 로그, 내보내기 결과에 나타나는 사례는 0건이어야 한다.

### 19.3 관찰 방법

- 구조 검증 성공과 실패 횟수를 원문 없이 로컬 세션 단위로 집계한다.
- 모델별 처리 시간, 첫 결과 시간, 실패 유형을 개발 검증에서 측정한다.
- 원격 텔레메트리는 MVP 범위에 포함하지 않는다.

## 20. 승인 테스트

### 20.1 정상 흐름

1. 런처에서 후기 분석 프로그램을 선택한다.
2. 서로 다른 감성의 후기 10건을 입력한다.
3. Ollama 모델과 동시 처리 수 4를 선택한다.
4. 분석을 시작하고 첫 완료 결과가 전체 종료 전에 표시되는지 확인한다.
5. 모든 성공 결과에 감성, 요약, 핵심 포인트, 전략, 답변 후보 3개가 있는지 확인한다.
6. 원본 순서로 정렬하고 CSV와 JSON을 내보낸다.

### 20.2 경계와 오류 흐름

- 빈 입력은 분석을 시작하지 않는다.
- 201건 입력은 MVP 제한 안내를 표시한다.
- 잘못된 CSV는 문제가 있는 열 또는 행을 표시한다.
- Ollama가 꺼진 상태에서는 연결 오류를 표시하고 작업을 시작하지 않는다.
- 한 요청에서 스키마 검증이 실패해도 다른 후기 결과는 유지한다.
- 분석 중 취소하면 새 호출을 시작하지 않고 완료 결과를 유지한다.
- 실패 항목 재시도 시 성공 항목의 호출 수가 증가하지 않는다.

### 20.3 런처 확장 흐름

1. 테스트용 프로그램 등록 정보를 추가한다.
2. 런처 공통 화면을 수정하지 않고 새 카드가 표시되는지 확인한다.
3. `coming_soon` 상태에서 실행이 차단되는지 확인한다.
4. 해당 프로그램 제거 후 후기 분석 기능이 그대로 동작하는지 확인한다.

| 장시간 작업 중 앱 종료 | sidecar 잔류, 결과 손실 | Rust가 프로세스 생명주기를 관리하고 종료 정리 테스트를 둔다. |
| 답변 후보의 부정확한 약속 | 고객 응대 위험 | 원문에 없는 보상, 환불, 일정 약속을 만들지 않도록 프롬프트와 경고를 적용한다. |
| 프로그램 증가로 런처 결합도 상승 | 변경 영향 확대 | 공통 등록 계약과 프로그램별 모듈 경계를 유지한다. |
| 후기 원문의 민감 정보 | 개인정보 노출 | 원문 로그 금지, 로컬 우선, 클라우드 전송 확인을 적용한다. |
| 후기 내용의 프롬프트 주입 | 지침 우회, 잘못된 결과 | 후기 원문을 데이터로 구분하고 도구 없는 구조화 체인과 적대적 입력 테스트를 적용한다. |
| CSV 수식 주입 | 내보낸 파일을 열 때 수식 실행 | 위험한 셀 시작 문자를 안전하게 처리하고 내보내기 테스트를 둔다. |
| 언어별 메시지 타입 불일치 | 런타임 파싱 실패, 상태 유실 | 버전이 있는 JSON Schema와 공통 계약 픽스처로 Python, Rust, TypeScript 호환성을 검증한다. |

## 26. 출시 승인 기준

MVP 출시는 다음 조건을 모두 만족해야 한다.

- 기능 요구사항의 `필수` 항목이 모두 승인 테스트를 통과한다.
- 실제 Tauri 앱에서 런처, 입력, 분석, 부분 실패, 재시도, 복사, 내보내기 흐름이 동작한다.
- Pydantic 구조 검증 실패를 성공으로 저장하지 않는다.
- 원본 순서 복원과 성공 결과 보존 테스트가 통과한다.
- 앱 종료 후 sidecar 프로세스가 남지 않는다.
- API 키와 후기 원문이 웹뷰와 일반 로그에 노출되지 않는다.
- 클라우드 모델 호출 전 외부 전송 안내와 확인이 동작한다.
- macOS 앱 또는 DMG 빌드와 설치 실행을 확인한다.
- README가 실제 구현 상태와 일치한다.
- Critical 또는 High 수준의 미해결 결함이 없다.

## 27. 구현 결정과 후속 항목

### 27.1 MVP에서 확정한 결정

1. Ollama를 기본값으로 사용하고 Groq와 OpenAI 어댑터를 선택 제공자로 둔다.
2. 최초 패키징 검증은 macOS arm64를 대상으로 한다.
3. 한 작업의 입력은 최대 200건, 후기 한 건은 최대 10,000자로 제한한다.
4. 답변 후보는 후기당 서로 다른 3개를 생성한다.
5. Python sidecar는 PyInstaller 단일 실행 파일로 패키징한다.
6. 브랜드 말투와 분석 결과는 현재 세션에서만 유지한다.
7. 클라우드 API 키는 웹뷰에 입력하거나 저장하지 않고 실행 환경 변수에서만 읽는다.

### 27.2 후속 결정이 필요한 항목

1. 분석 결과를 세션 종료 후에도 보존할 로컬 데이터베이스를 도입할지
2. 운영체제 자격 증명 저장소를 사용할지
3. Windows와 Linux 설치 파일을 어느 순서로 지원할지
4. Apple Developer ID 서명, 공증, 자동 업데이트를 어느 배포 단계에서 도입할지
5. 브랜드 말투를 재사용 가능한 프로필로 저장할지
