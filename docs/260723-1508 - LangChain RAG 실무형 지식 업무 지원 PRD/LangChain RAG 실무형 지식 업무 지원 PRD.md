# LangChain RAG 실무형 지식 업무 지원 PRD

## 1. 문서 목적

이 문서는 기존 ReviewFlow Desktop을 로컬 회사 문서 기반의 지식 업무 지원 프로그램으로 확장하기 위한 제품 요구사항을 정의합니다.

첫 버전은 사용자가 선택한 로컬 문서 폴더를 공통 지식베이스로 구축하고 다음 두 업무를 동등하게 지원합니다.

- 사내 문서 질의응답
- 상품 후기 분석 및 근거 기반 답변 생성

기존 상품 후기 분석 기능은 유지합니다. 새 기능은 기존 분석 결과에 회사 문서 검색과 근거 검증을 결합하는 확장 기능으로 제공합니다.

## 2. 제품 개요

### 2.1 제품 한 줄 정의

로컬 회사 문서를 검색 가능한 지식베이스로 만들고, 사내 질문과 고객 후기 답변에 확인 가능한 근거를 제공하는 LangChain RAG 기반 Tauri 데스크톱 앱입니다.

### 2.2 해결하려는 문제

회사 실무에서는 상품 설명, 배송 정책, 교환 및 환불 기준, 고객 응대 지침과 업무 매뉴얼이 여러 파일에 흩어져 있습니다. 담당자는 질문이나 후기를 처리할 때 관련 문서를 직접 찾아야 하며, LLM만 사용하면 문서에 없는 내용을 사실처럼 생성할 위험이 있습니다.

이 제품은 다음 문제를 해결합니다.

- 여러 로컬 문서에서 필요한 내용을 찾는 시간이 오래 걸립니다.
- 같은 질문에도 담당자마다 다른 기준으로 답변합니다.
- 후기 답변을 만들 때 회사 정책과 충돌하는 약속이 포함될 수 있습니다.
- LLM 답변이 어떤 문서를 근거로 생성됐는지 확인하기 어렵습니다.
- 단순 LLM 호출만으로는 검색, 재검색, 검증과 승인 과정을 일관되게 운영하기 어렵습니다.

### 2.3 제품 가치

- 로컬 문서를 외부 저장소에 업로드하지 않고 검색할 수 있습니다.
- 답변마다 파일명과 페이지 또는 행 정보를 표시합니다.
- 자료에 없는 내용은 추측하지 않고 근거 부족 상태로 처리합니다.
- 사내 질의응답과 후기 답변 생성이 같은 지식베이스를 사용합니다.
- LangChain을 문서 처리, 검색, 체인 조합과 구조화 출력의 중심 계층으로 사용합니다.
- LangGraph를 재검색, 근거 검증과 사용자 승인 상태를 관리하는 데 사용합니다.

## 3. 목표와 비목표

### 3.1 첫 버전 목표

1. PDF, Markdown, TXT, CSV 파일을 로컬 지식베이스로 색인합니다.
2. `bge-m3` 임베딩과 FAISS를 사용하여 관련 문서 조각을 로컬에서 검색합니다.
3. 사내 질문에 출처가 포함된 답변을 생성합니다.
4. 기존 후기 분석에 상품 및 회사 정책 검색을 연결합니다.
5. 후기 답변에 사용된 근거와 검증 상태를 표시합니다.
6. 검색 근거가 부족하면 답변 생성을 중단하거나 사용자 검토 상태로 전환합니다.
7. 문서 변경과 삭제를 감지하여 지식베이스를 갱신합니다.
8. Tauri 패키지에 Python sidecar를 포함하여 별도 Python 설치 없이 실행합니다.

### 3.2 첫 버전 비목표

- 상품 URL에서 후기 자동 수집
- Google Drive와 Notion 직접 연동
- 스캔 이미지의 OCR 처리
- 사용자 및 부서별 문서 접근 권한
- 고객센터나 쇼핑몰에 답변 자동 게시
- 자유롭게 도구를 선택하고 실행하는 범용 Agent
- 클라우드 벡터 데이터베이스 운영
- 여러 사용자가 동시에 접속하는 서버형 서비스

## 4. 대상 사용자

### 4.1 핵심 사용자

- 상품 후기와 고객 문의에 답변하는 운영 담당자
- 상품, 배송, 교환 및 환불 정책을 확인하는 고객지원 담당자
- 사내 업무 규정과 매뉴얼을 자주 검색하는 실무자
- 외부 전송 없이 로컬 LLM을 활용해야 하는 조직

### 4.2 주요 사용자 요구

- 별도 개발 도구 없이 폴더를 선택하고 색인을 시작할 수 있어야 합니다.
- 답변이 어떤 문서를 참고했는지 즉시 확인할 수 있어야 합니다.
- 문서에 근거가 없는 답변을 사실처럼 표시하지 않아야 합니다.
- 기존 후기 분석 기능과 새 RAG 기능을 한 앱에서 사용할 수 있어야 합니다.
- Ollama가 실행되지 않거나 모델이 없을 때 해결 방법을 확인할 수 있어야 합니다.

## 5. 제품 원칙

1. 로컬 우선: 문서 임베딩과 벡터 검색은 항상 사용자 컴퓨터에서 처리합니다.
2. 근거 우선: 답변보다 검색 근거와 출처를 먼저 확보합니다.
3. 근거 없음의 명시: 자료가 없으면 추측하지 않고 확인할 수 없다고 표시합니다.
4. 결정 가능한 작업의 코드화: 라우팅, 재시도 횟수, 점수 비교와 상태 전환은 코드로 처리합니다.
5. 제한된 LLM 역할: LLM은 질문 정리, 관련성 판단, 생성과 검증에만 사용합니다.
6. 사용자 승인: 생성된 후기 답변은 사용자가 승인하기 전 외부로 전송하지 않습니다.
7. 신뢰할 수 없는 입력: 문서와 후기 안의 명령문을 시스템 지침으로 실행하지 않습니다.
8. 추적 가능한 결과: 검색 문서, 모델, 처리 시간과 검증 상태를 결과에 포함합니다.

## 7. 전체 사용자 흐름

### 7.1 지식베이스 생성

1. 사용자가 런처에서 `지식베이스 관리`를 선택합니다.
2. 사용자가 로컬 문서 폴더를 선택합니다.
3. 앱이 지원 파일과 제외 파일을 미리 보여줍니다.
4. CSV 파일이 있으면 사용자가 검색 대상 열을 선택합니다.
5. 앱이 파일을 읽고 문서 조각으로 분할합니다.
6. Python sidecar가 `bge-m3`로 임베딩을 생성합니다.
7. FAISS 인덱스와 SQLite 문서 목록을 앱 데이터 디렉터리에 저장합니다.
8. 화면에 처리 파일 수, 실패 파일, 생성 조각 수와 마지막 갱신 시간을 표시합니다.

### 7.2 사내 문서 질의응답

1. 사용자가 `사내 문서 질의응답`을 선택합니다.
2. 사용자가 업무 질문을 입력합니다.
3. 앱이 질문을 검색용 표현으로 정리합니다.
4. Retriever가 관련 문서 후보를 검색합니다.
5. 관련성 평가기가 답변에 사용할 근거를 선별합니다.
6. 근거가 부족하면 질문을 한 번 재작성하여 다시 검색합니다.
7. 충분한 근거가 있으면 답변 생성 체인이 답변과 인용을 생성합니다.
8. 근거 검증 체인이 답변의 주요 주장이 검색 문서에 포함되는지 확인합니다.
9. 화면에 답변, 출처, 근거 부족 내용, 모델과 처리 시간을 표시합니다.

### 7.3 후기 근거 답변 생성

1. 사용자가 기존 `상품 후기 분석` 화면에 후기와 상품명을 입력합니다.
2. 기존 LangChain 체인이 감성, 요약, 핵심 문제와 기본 답변 전략을 분석합니다.
3. 상품명과 후기 분석 결과를 이용하여 지식 검색 질문을 만듭니다.
4. 상품 설명, 배송, 교환, 환불과 고객 응대 지침을 검색합니다.
5. 검색 근거를 포함하여 고객 답변 후보를 생성합니다.
6. 검증 체인이 정책에 없는 환불, 보상, 교환 약속을 검사합니다.
7. 답변마다 근거 문서와 검증 상태를 표시합니다.
8. 사용자가 답변을 수정하거나 승인합니다.
9. 첫 버전에서는 승인된 답변을 복사할 수 있지만 외부 시스템으로 자동 전송하지 않습니다.

## 8. 기능 요구사항

### 8.1 지식베이스 관리

| ID | 요구사항 | 우선순위 | 승인 기준 |
| --- | --- | --- | --- |
| KB-001 | 사용자가 로컬 폴더를 선택하여 색인을 시작한다. | 필수 | 사용자가 선택하지 않은 경로를 읽지 않는다. |
| KB-002 | PDF, Markdown, TXT, CSV 파일을 지원한다. | 필수 | 각 파일 형식의 정상 샘플이 색인된다. |
| KB-003 | 지원하지 않는 파일은 이유와 함께 제외한다. | 필수 | 전체 작업을 중단하지 않고 제외 목록에 표시한다. |
| KB-004 | CSV는 미리보기 후 검색 대상 열을 선택한다. | 필수 | 선택하지 않은 열은 임베딩 원문에 포함하지 않는다. |
| KB-005 | 문서를 기본 800자, 120자 중첩으로 분할한다. | 필수 | 문서 조각에 원본 위치와 순번이 남는다. |
| KB-006 | 파일 해시와 수정 시간을 저장한다. | 필수 | 변경되지 않은 파일은 다시 임베딩하지 않는다. |
| KB-007 | 삭제된 파일을 다음 갱신에서 제거한다. | 필수 | 삭제된 파일의 조각이 검색되지 않는다. |
| KB-008 | 일부 파일 실패를 전체 색인 실패로 처리하지 않는다. | 필수 | 성공 파일은 검색 가능하고 실패 파일은 따로 표시된다. |
| KB-009 | 진행률과 취소 기능을 제공한다. | 권장 | 취소 후 완료된 파일 상태가 손상되지 않는다. |
| KB-010 | 마지막 색인 시간과 통계를 표시한다. | 필수 | 파일 수, 조각 수와 실패 수가 실제 저장 상태와 일치한다. |

### 8.2 로컬 벡터 검색

| ID | 요구사항 | 우선순위 | 승인 기준 |
| --- | --- | --- | --- |
| SEARCH-001 | `bge-m3`로 문서 임베딩을 생성한다. | 필수 | 외부 임베딩 API를 호출하지 않는다. |
| SEARCH-002 | FAISS 인덱스를 앱 데이터 디렉터리에 저장한다. | 필수 | 앱을 다시 실행해도 재색인 없이 검색할 수 있다. |
| SEARCH-003 | 질문당 후보 12개를 검색한다. | 필수 | 검색 설정이 실행 계약과 테스트에 명시된다. |
| SEARCH-004 | MMR로 후보를 8개까지 줄인다. | 필수 | 같은 문서의 유사 조각이 결과를 독점하지 않는다. |
| SEARCH-005 | 관련성 평가로 최대 5개 근거를 선택한다. | 필수 | 구조화 스키마를 통과한 결과만 사용한다. |
| SEARCH-006 | 근거 점수가 기준보다 낮으면 근거 부족으로 처리한다. | 필수 | 빈 검색 결과로 답변을 생성하지 않는다. |
| SEARCH-007 | 검색 결과에 파일명과 원본 위치를 포함한다. | 필수 | PDF 페이지 또는 CSV 행을 확인할 수 있다. |

### 8.3 사내 문서 질의응답

| ID | 요구사항 | 우선순위 | 승인 기준 |
| --- | --- | --- | --- |
| QA-001 | 사용자가 자연어 질문을 입력할 수 있다. | 필수 | 빈 질문과 최대 길이 초과 질문을 분석 전에 차단한다. |
| QA-002 | 검색 질문을 구조화하여 생성한다. | 필수 | 원래 질문과 검색 질문을 작업 상태에 보존한다. |
| QA-003 | 검색 결과가 부족하면 한 번만 재검색한다. | 필수 | 반복 횟수가 코드로 제한된다. |
| QA-004 | 검색 근거만 사용하여 답변한다. | 필수 | 답변의 주요 주장에 하나 이상의 근거가 연결된다. |
| QA-005 | 자료에 없는 질문은 정해진 근거 부족 문구로 응답한다. | 필수 | `현재 등록된 자료에서 확인할 수 없습니다`를 표시한다. |
| QA-006 | 파일명과 원본 위치를 인용으로 표시한다. | 필수 | 사용자가 출처 목록에서 근거 내용을 확인할 수 있다. |
| QA-007 | 모델, 처리 시간과 검증 상태를 표시한다. | 권장 | 진단 정보에 원문과 비밀값을 기록하지 않는다. |

| REVIEW-RAG-002 | 지식베이스 사용 여부를 사용자가 선택한다. | 필수 | 색인이 없으면 실행 전에 안내한다. |
| REVIEW-RAG-003 | 상품명과 후기 분석을 검색 질문으로 변환한다. | 필수 | 후기 안의 명령문을 검색 지침으로 취급하지 않는다. |
| REVIEW-RAG-004 | 답변 후보마다 사용한 정책 근거를 표시한다. | 필수 | 근거 ID가 실제 검색 결과와 일치한다. |
| REVIEW-RAG-005 | 확인되지 않은 약속을 검증한다. | 필수 | 정책에 없는 환불, 보상, 교환 약속을 승인 상태로 표시하지 않는다. |
| REVIEW-RAG-006 | 사용자가 답변을 승인하거나 수정할 수 있다. | 필수 | 승인 전 자동 외부 전송이 발생하지 않는다. |
| REVIEW-RAG-007 | 근거가 부족한 답변을 검토 필요 상태로 표시한다. | 필수 | 부족 사유와 확인할 문서를 표시한다. |

## 9. 시스템 아키텍처

### 9.1 권장 구조

```text
React UI
  ↓ Tauri invoke
Rust command and contract validation
  ↓ JSONL over stdin/stdout
Python sidecar
  ├─ document loaders
  ├─ text splitter
  ├─ SQLite document catalog
  ├─ OllamaEmbeddings(bge-m3)
  ├─ FAISS vector store
  ├─ LangChain retrieval chains
  ├─ LangGraph validation workflow
  └─ ChatOllama(gemma4:e2b)
  ↓ structured events
Rust event validation
  ↓ Tauri event
React result and source display
```

### 9.2 구성 요소 책임

#### React

- 폴더와 파일 선택
- CSV 열 미리보기와 선택
- 색인 진행률, 실패 파일과 상태 표시
- 질문과 후기 입력
- 답변, 출처, 검증 상태와 승인 UI

#### Rust Tauri

- 사용자 선택 경로 전달
- 최소 권한과 경로 범위 관리
- Python sidecar 실행, 취소와 종료
- 요청 및 이벤트 계약 검증
- 웹뷰에 비밀값과 직접 파일 접근 권한을 노출하지 않음

#### Python sidecar

- 문서 로딩, 정제와 분할
- 해시 계산과 SQLite 문서 상태 관리
- 임베딩 생성과 FAISS 저장
- LangChain 검색, 생성과 구조화 출력
- LangGraph 상태 전환
- JSONL 진행 및 결과 이벤트 출력

#### Ollama

- `bge-m3` 문서와 질문 임베딩
- `gemma4:e2b` 질문 정리, 관련성 평가, 답변 생성과 근거 검증

### 9.3 LangChain 책임

- 파일 형식별 문서 로더 연결
- `RecursiveCharacterTextSplitter` 기반 문서 분할
- `OllamaEmbeddings` 기반 임베딩
- FAISS Retriever 구성
- MMR 검색
- `ChatPromptTemplate`과 LCEL 체인
- `RunnableParallel` 기반 독립 입력 처리
- Pydantic 구조화 출력
- 제공자별 Chat Model 추상화
- 배치 실행과 동시성 제한

### 9.4 LangGraph 책임

```text
retrieve
  ↓
grade_documents
  ├─ 충분함 → generate
  └─ 부족함 → rewrite_query
                  ↓
            retrieve_once_more
                  ↓
               generate
                  ↓
          validate_grounding
          ├─ approved
          ├─ needs_review
          └─ insufficient_evidence
```

- 재검색은 최대 한 번만 허용합니다.
- 검색 결과 개수, 재검색 횟수와 상태 라우팅은 코드가 결정합니다.
- LLM은 검색어 재작성, 관련성 판단, 답변 생성과 근거 검증만 수행합니다.
- 임의 웹 검색, 파일 쓰기, 셸 실행 도구를 연결하지 않습니다.

## 11. 색인 정책

### 11.1 파일 처리

- 사용자가 명시적으로 선택한 폴더만 처리합니다.
- 심볼릭 링크는 첫 버전에서 따라가지 않습니다.
- 지원하지 않는 확장자는 제외합니다.
- 읽기 실패와 파싱 실패를 구분합니다.
- 하나의 파일 실패가 정상 파일의 색인을 취소하지 않습니다.

### 11.2 분할

- 기본 조각 크기는 800자입니다.
- 기본 중첩 크기는 120자입니다.
- PDF 페이지 경계를 메타데이터에 보존합니다.
- Markdown 제목을 가능한 경우 조각 메타데이터에 포함합니다.
- CSV 한 행을 기본 문서 단위로 취급하고 선택한 열만 결합합니다.

### 11.3 변경 감지

- 파일 경로, 수정 시간과 내용 해시를 비교합니다.
- 변경되지 않은 파일은 기존 벡터를 재사용합니다.
- 변경된 파일은 기존 조각을 제거한 후 다시 색인합니다.
- 삭제된 파일은 SQLite와 FAISS 검색 대상에서 제거합니다.
- 중단된 색인은 완료된 이전 인덱스를 손상시키지 않도록 임시 인덱스에 작성한 후 교체합니다.

## 12. 검색과 답변 정책

### 12.1 검색

1. 질문을 임베딩합니다.
2. FAISS에서 후보 12개를 검색합니다.
3. MMR로 8개를 선택합니다.
4. 구조화 관련성 평가기로 최대 5개를 선택합니다.
5. 관련 근거가 없으면 `insufficient_evidence`를 반환합니다.

### 12.2 재검색

- 첫 검색 결과가 부족한 경우에만 질문을 재작성합니다.
- 재작성된 질문은 원래 의미를 확장할 수 있지만 새로운 사실을 추가할 수 없습니다.
- 재검색은 최대 한 번 실행합니다.
- 두 번째 검색도 부족하면 답변을 생성하지 않습니다.

### 12.3 답변

- 검색된 근거만 사용합니다.
- 인용 식별자가 없는 사실 주장을 최종 답변에 포함하지 않습니다.
- 자료에서 확인할 수 없는 부분은 별도로 표시합니다.
- 관련 자료가 없으면 `현재 등록된 자료에서 확인할 수 없습니다`라고 표시합니다.
- 후기 답변은 공감 표현과 정책 근거를 구분합니다.
- 확인되지 않은 보상, 환불, 교환과 배송 일정을 약속하지 않습니다.

## 13. 보안과 개인정보

### 13.1 로컬 처리

- 문서 임베딩과 벡터 검색은 항상 로컬에서 처리합니다.
- FAISS와 SQLite 파일은 운영체제의 앱 데이터 디렉터리에 저장합니다.
- 사용자가 선택하지 않은 폴더를 스캔하지 않습니다.

### 13.2 클라우드 모델

- 기본 생성 제공자는 Ollama입니다.
- Groq 또는 OpenAI 사용 전 전송되는 데이터 범위를 표시합니다.
- 사용자가 현재 작업의 원문 전송에 동의한 경우에만 클라우드 모델을 호출합니다.
- 임베딩은 클라우드 모델 선택과 관계없이 로컬 `bge-m3`를 사용합니다.

### 13.3 로그

다음 정보를 로그에 기록하지 않습니다.

- 문서 원문
- 후기 원문
- 검색 결과 전문
- API 키
- 인증 헤더
- 사용자 개인 정보

로그에는 작업 식별자, 상태, 처리 개수, 오류 코드와 처리 시간만 기록합니다.

### 13.4 프롬프트 인젝션

- 문서와 후기를 신뢰할 수 없는 데이터로 명시합니다.
- 문서 안의 지시를 시스템 명령으로 따르지 않습니다.
- RAG 체인에 웹 검색, 파일 쓰기와 셸 실행 도구를 연결하지 않습니다.
- 모델 출력은 실행 가능한 명령으로 취급하지 않습니다.
- Pydantic 스키마를 통과한 결과만 Rust와 React에 전달합니다.

## 16. 비기능 요구사항

### 16.1 성능

- 10,000개 문서 조각에서 검색 p95는 기준 장비에서 2초 이하를 목표로 합니다.
- LLM 생성 시간은 검색 시간과 분리하여 측정합니다.
- 색인 중 진행 이벤트를 지속적으로 표시합니다.
- 동일 파일 재색인 시 변경되지 않은 임베딩을 재생성하지 않습니다.

### 16.2 신뢰성

- 일부 파일 실패가 정상 문서의 검색 기능을 제거하지 않습니다.
- 색인 교체 도중 앱이 종료되어도 마지막 정상 인덱스를 유지합니다.
- 재검색은 최대 한 번으로 제한합니다.
- 성공 결과와 실패 결과를 작업 단위로 구분합니다.

### 16.3 사용성

- 개발 도구 없이 폴더 선택부터 첫 질문까지 완료할 수 있어야 합니다.
- 출처를 답변과 가까운 위치에서 확인할 수 있어야 합니다.
- 오류 메시지는 사용자가 다음 행동을 알 수 있도록 작성합니다.
- 취소와 재시도 상태를 명확히 표시합니다.

### 16.4 호환성

- macOS를 첫 패키징 및 실제 표면 검증 대상으로 합니다.
- 기존 Tauri v2, React, TypeScript, Rust와 Python sidecar 구조를 유지합니다.
- 앱 설치 후 별도 Python 설치를 요구하지 않습니다.

## 17. 성공 지표

### 17.1 제품 지표

- 사용자가 앱에서 로컬 폴더를 선택하여 지식베이스를 만들 수 있습니다.
- 사용자가 질문 답변에서 파일과 원본 위치를 확인할 수 있습니다.
- 사용자가 후기 답변에서 정책 근거와 검증 상태를 확인할 수 있습니다.

### 17.2 품질 지표

- 선별한 평가 질문 30개에서 출처 정확도 95% 이상
- 근거 없는 평가 질문 10개에서 임의 답변 생성률 0%
- 정상 모델 응답의 구조화 스키마 검증 성공률 95% 이상
- 일부 파일 실패 시 정상 색인 보존율 100%
- 변경되지 않은 파일의 중복 색인 발생률 0%
- 삭제된 파일이 검색 결과에 남는 비율 0%

### 17.3 관찰 항목

- 파일 형식별 색인 성공률
- 색인 파일 수와 문서 조각 수
- 검색 시간과 생성 시간
- 첫 검색에서 근거를 찾은 비율
- 재검색 실행률
- 근거 부족 응답률

## 19. 승인 테스트

### 19.1 정상 흐름

1. 사용자가 네 가지 지원 파일 형식이 포함된 폴더를 선택합니다.
2. 모든 정상 파일이 색인되고 파일 수와 조각 수가 표시됩니다.
3. 사용자가 문서 내용으로 답할 수 있는 질문을 입력합니다.
4. 답변에 정확한 파일명과 페이지 또는 행이 표시됩니다.
5. 사용자가 상품 후기를 입력하고 지식베이스 사용을 켭니다.
6. 답변 후보에 정책 근거와 검증 상태가 표시됩니다.

### 19.2 변경과 삭제

1. 같은 폴더를 다시 색인합니다.
2. 중복 문서가 생성되지 않습니다.
3. 파일 하나를 수정한 후 갱신합니다.
4. 수정된 파일만 다시 처리됩니다.
5. 파일 하나를 삭제한 후 갱신합니다.
6. 삭제된 파일이 검색 결과에서 제거됩니다.

### 19.3 근거 부족

1. 등록 문서와 관련 없는 질문을 입력합니다.
2. 앱이 임의 답변을 생성하지 않습니다.
3. `현재 등록된 자료에서 확인할 수 없습니다`를 표시합니다.
4. 후기 답변에서 정책에 없는 보상을 요구합니다.
5. 검증 상태가 `needs_review` 또는 `insufficient_evidence`로 표시됩니다.

### 19.4 오류와 복구

1. 손상된 PDF가 포함된 폴더를 색인합니다.
2. 정상 파일은 검색할 수 있고 손상 파일만 실패 목록에 표시됩니다.
3. 색인 중 작업을 취소합니다.
4. 이전 정상 인덱스가 유지됩니다.
5. Ollama를 종료하고 질문을 실행합니다.
6. 연결 실패와 해결 방법이 표시됩니다.
